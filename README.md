# FoodWise

نظام يساعد مدير الفرع يعرف كل صباح: وش المنتجات اللي بتنهدر، وكم بتكلف، ووش يسوي اليوم عشان ينقذها.

## التشغيل

```bash
cd ~/Downloads/FoodWise
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python app.py
```

ثم افتحي http://127.0.0.1:5050 (صفحة المدير) و http://127.0.0.1:5050/charity (بوابة الجمعية).

البيانات والنتائج جاهزة داخل المجلد. لإعادة الحساب من البداية (يمسح قرارات اليوم):

```bash
python -m foodwise.pipeline --regenerate
```

الاختبارات: `python -m unittest discover -s tests -t .`

### النشر على Render

المستودع فيه `render.yaml`: من Render اختاري New ← Blueprint ← هذا المستودع، فيُثبَّت ويُشغَّل تلقائيًا
(`gunicorn app:app`). النسخة المجانية تنام بعد 15 دقيقة بدون زيارات، وقرارات الزوار ترجع للبداية عند إعادة التشغيل.

## الصفحات

| الصفحة | ماذا تعرض |
|---|---|
| قائمة الإنقاذ اليوم | المنتجات المتوقع هدرها، الصلاحية، الكمية والقيمة، الأولوية، القرار المقترح، وزر اعتماد أو رفض. الضغط على المنتج يعرض السبب. وتحتها: طلبات استلام التبرعات، والتبرعات المتوقعة خلال 7 أيام مع إشعار مسبق للجمعية. |
| توقع الهدر | الهدر المتوقع لفترة يختارها المدير (3 أيام حتى شهر) بالريال والكيلو، أكثر المنتجات هدرًا، وتفاصيل كل منتج مع فلتر الفئة. |
| طلبية المخزون القادمة | لكل منتج: موعد التوريد، البيع المتوقع، المخزون وقت الوصول، الطلبية المعتادة مقابل المقترحة، والفرق بالكرتون. مع رسم المبيعات والتوقع وزر اعتماد الطلبية. |
| أثر الفرع | القيمة المحفوظة، نسبة الهدر من المبيعات مقارنة بما قبل FoodWise، القرارات المنفذة في وقتها، التبرعات بالكيلو، نسبة الهدر الأسبوعية قبل FoodWise وبعده، والهدر حسب الفئة، ونتائج القرارات حسب نوعها. |
| بوابة الجمعية (`/charity`) | طلبات الاستلام اليوم مع تأكيدها وتسجيل استلامها، والتبرعات المتوقعة التي أرسل عنها الفرع إشعارًا مسبقًا مع الرد عليها، وما استلمته الجمعية هذا الشهر. |

## ما الذي يعمل خلف الشاشة (للعرض أمام لجنة التحكيم)

- **تعلم آلة:** توقع الطلب اليومي لكل منتج حتى 30 يومًا، باستخدام: يوم الأسبوع، قرب الراتب، الحرارة المتوقعة، نوع اليوم (عادي، رمضان، عيد، إجازة حسب تقويم أم القرى والتقويم الدراسي)، ومبيعات الأسابيع السابقة.
  نقارن نموذجين (Gradient Boosting وRandom Forest) بطريقتين بسيطتين على آخر 6 أسابيع لم يرها التدريب، ونستخدم الأدق تلقائيًا
  (مقارنة مستقلة للأيام 1-7 وللأيام 8-30). النتائج في `data/out/model_report.json`، والتحقق من حساب الهدر في `data/out/waste_backtest.json`.
- **محاكاة:** الأيام القادمة تُحاكى 200 مرة (بيع من الأقرب انتهاءً + التوريدات القادمة)، لحساب الهدر المتوقع لكل دفعة ومنتج.
- **قواعد القرار** حسب ما بقي على الصلاحية: 3 أيام ← نقل لقسم Eat Fresh (خضار وفواكه) أو لواجهة العرض؛ يومان ← تبرع مخطط له بالكمية المتوقع ألا تُباع حتى مع الخصم وخصم 25% على الباقي (يوم للمنتج الذي صلاحيته 3 أيام، ولا تبرع بالخبز الطازج)؛ يوم ← خصم 35%؛ ينتهي اليوم ← خصم 50% حتى الإغلاق. ويستطيع المدير رفض المقترح واختيار بديل أو تعديل قراره. كل الافتراضات في `foodwise/config.py`.
- **التكامل مع الجمعيات:** اعتماد قرار تبرع يُنشئ طلب استلام للجمعية تلقائيًا، وتؤكده الجمعية وتسجل استلامه من بوابتها، فتتحدث الحالة عند المدير تلقائيًا، والتسليم يُحتسب في أثر الفرع مباشرة.
  ومن المحاكاة نعرف التبرعات المخطط لها في الأيام السبعة القادمة، فيرسل المدير إشعارًا مسبقًا وترد الجمعية (ستستلم / لا تستطيع).
- **البيانات:** بيانات تجريبية لفرع واحد بنفس شكل بيانات الفرع الحقيقية (مبيعات، دفعات، هدر، طقس)، وتُستبدل بالبيانات الحقيقية لاحقًا.

tests/                 الاختبارات
